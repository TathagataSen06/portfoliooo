Application Report

GraphSentinel: Finding Layering and Round-Trips in a Transaction Graph

Tathagata Sen, with team Demo Buddies (4 people) · Source on GitHub

ABSTRACT

Rule-based anti-money-laundering checks look at transactions one at a time, so they miss patterns that only exist across accounts: money hopping through a chain of new accounts, or leaving and coming back in a loop. GraphSentinel, built by a team of four for iDEA 2.0 (Union Bank of India, problem statement PS3), treats transactions as a time-windowed graph. Graph walks find layering chains, round-trips and structuring; a graph + sequence model scores accounts; investigators get a D3 fund-flow view and a goAML report export. Everything was built and evaluated on synthetic data.

The team README lists your role as graph analytics & database engineering. Name exactly what you built (the schema? the graph-walk detectors? the fund-flow view?). Interviewers will ask, so be specific.

1Problem

The problem statement asked for five patterns:

  • Multi-hop layering: funds moving rapidly through three or more accounts.
  • Circular round-trips: money that leaves an account and comes back.
  • Structuring: clusters of transfers kept just under the ₹10 lakh reporting threshold.
  • Dormant reactivation: an account silent for months that suddenly moves money.
  • KYC mismatch: behaviour that doesn't fit the customer's declared profile.

The first two are invisible to per-transaction rules; they're paths in a graph.

2Approach

2.1Graph walks over a time window

Transactions inside the window become an adjacency list keyed by sender, with each account's outgoing edges sorted by time. A depth-first walk extends chains forward. A chain becomes a layering alert when it touches at least four accounts within 48 hours and, on average, each hop passes on at least 90% of what it received:

if (timeSpanHours <= (pattern.time_window_hours || 48) && uniqueAccounts >= 4 && forwardRatio >= 0.9) {
  // ...
  const confidence = clamp(0.56 + path.length * 0.05 + forwardRatio * 0.2 + shellAccounts * 0.04, 0, 0.97);
backend/lib/detection.mjs

Round-trips use a 72-hour window and need at least 75% of the money to return. Dormant reactivation needs 180+ days of silence. Every alert carries a plain-language narrative and the factors behind it, so an investigator sees why, not just a score.

2.2A learned scorer

The model takes two views of an account. A GRU evolves over the last 10 graph snapshots (8 aggregate features each), an EvolveGCN-inspired block. Two LSTM layers read the account's last 24 transactions (11 features: amount, direction, time gap, channel, risk score, account age). The two encodings are fused into a nine-way classifier (normal plus eight patterns), and an LSTM decoder reconstructs the transaction sequence so unusual behaviour shows up as reconstruction error.

6What I'd Change

Found by reading the code. Keep, edit or drop each one:

  • Test on data the generator didn't write. IBM's public AML transaction dataset (synthetic, but from an independent generator) or the Elliptic Bitcoin dataset (real, labelled) would show whether the detectors generalise.
  • Calibrate the confidence. Alert confidence is a hand-tuned formula (0.56 plus 0.05 per hop, and so on), so a score of 0.8 doesn't mean 80%. Fit it against labelled outcomes.
  • Windows are relative to now. The detectors filter on Date.now(), so replaying last month's transactions finds nothing. Anchoring windows to event time would make backtesting possible.
