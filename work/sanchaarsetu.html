01At a glance

A business in Karnataka updates its details once, on the Single Window System (SWS), but dozens of department systems each keep their own copy. SanchaarSetu sits between them: it takes changes in by webhook or polling, drops duplicates, maps fields between schemas, holds conflicting updates for review, delivers through Kafka with retries, and writes every step to a hash-chained audit log.

40+department systems to keep in sync

02The problem

Factories, BBMP, Commercial Taxes, Fire Safety: each department runs its own software, from its own vendor, on its own database. When a business changes its registered address or its authorised signatory on the SWS, those copies drift apart, and someone re-enters the change by hand, department by department.

The obvious fix, one master database everyone reads and writes, isn't available. Departments have vendor contracts and workflows of their own, and direct database access to 40 systems is a security and bureaucratic non-starter. That constraint shaped everything: SanchaarSetu can only call APIs, receive webhooks, or poll. It's an adapter, not a replacement.

    04Design decisions

    Each choice traded something away. These are the ones that shaped the system, from the repository's own trade-off notes.

    4.1

    Idempotency by time window

    Source systems retry, so the same change arrives more than once. Remembering every event would grow forever, so the key hashes the business ID, event type and current 60-second window.

    Trade-off: a genuine second change to the same field inside a minute is dropped. Addresses don't change twice a minute.

    4.2

    Accept now, deliver later

    The webhook answers straight away and hands the event to Kafka, so five departments being down can't fail the SWS request.

    Trade-off: the SWS can't tell the user immediately whether every department got the update. That status lives on the dashboard.

    4.3

    Learned field mapping, human gate

    sentence-transformers match field names like registered_address to address. Scores of 0.85 or more apply automatically; lower ones wait for review. Emails, phone, Aadhaar and PAN numbers are scrubbed first.

    Trade-off: AI adds non-determinism, so approved mappings are stored and reused rather than re-inferred.

    4.4

    A 60-second conflict window

    If the SWS and a department change the same business within 60 seconds, delivery is held and an operator resolves it: SWS wins, last write wins, or a manual choice.

    Trade-off: updates 65 seconds apart are simply applied in order.

    The idempotency key, as written

    app/full_main.py
    def make_idempotency_key(ubid: str, event_type: str, ts: float, window_seconds: int = 60) -> str:
    window = int(ts // window_seconds)
    raw = f"{ubid}:{event_type}:{window}"
    return hashlib.sha256(raw.encode()).hexdigest()

ok = await redis_client.set(idemp, "1", ex=3600, nx=True)

    An audit log you can't quietly edit

    Every audit row stores the previous row's hash and a SHA-256 over that hash plus its own fields. Change any past row and every hash after it stops matching.

    06Results

    An end-to-end suite (test_e2e.py) runs nine scenarios against the Docker Compose stack: SWS-to-department propagation, duplicate rejection, signatory and GSTIN updates, a simultaneous-update conflict through to resolution and requeue, a batch across many businesses, change-detection ingest, and DLQ replay.

    The project won the AI for Bharat Hackathon (PAN IIT, ₹1,00,000) and was recognised by the Joint Directors of Karnataka's Department of Industry & Commerce.

    07What I'd change

    Found by reading the code. Keep, edit or drop each one:

    • Retries block the queue. The backoff is an asyncio.sleep inside the only consumer loop, so one department that's down holds up every other department's deliveries for up to 30 s per message. A delayed retry topic keeps the main loop moving.
    • No partition key. Events are produced without a key, so Kafka doesn't keep one business's events in order, and the in-memory conflict window only works with a single consumer. Keying by business ID fixes both.
    • The audit chain can fork. The writer reads the last hash, then inserts separately; two writers at once can chain off the same parent. An advisory lock or a single INSERT … SELECT closes the gap.
    • Silent drops. A department that returns 200 OK but discards the update is invisible today. A reconciliation job comparing SWS and department state would catch it.
